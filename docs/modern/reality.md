# VLESS 与 XTLS-Reality：无需域名的借壳伪装

> “大隐隐于市。最好的加密流量，就是世界上最庞大的合法加密流量本身。”

在 2022 年之前，如果你想搭建一个抗封锁的高伪装节点，标准答案通常是：**买一个境外域名 + 申请 Let's Encrypt 证书 + 搭建 Nginx 反向代理 + 配置 V2Ray WebSocket + TLS**。

这套方案不仅配置繁琐、动辄证书过期，而且面临一个致命逻辑矛盾：**为什么一个每天只有几个 PV 的生僻个人小博客，常年保持着几百 GB 的长连接海外流量？**

为了彻底解决这一痛点，**XTLS 团队推出了革命性的 Reality 协议**。

---

## 一、什么是 Reality？

**Reality 是基于 VLESS 协议的一种新型传输安全机制（Transport Security）**。

它最大的颠覆在于：
1. **不需要自己购买域名**；
2. **不需要自己申请或续期 SSL/TLS 证书**；
3. **消除服务端 TLS 指纹特征**；
4. **具备完美抵御 GFW 主动探测（Active Probing）的能力**。

---

## 二、核心工作原理剖析

Reality 的核心逻辑被称为**“借壳生蛋（SNI 借用）”**。

它在服务器配置中指定一个真实存在的合规海外大厂网站（例如苹果官网 `gateway.icloud.com`、微软官网 `www.microsoft.com`、雅虎等）作为 **目标网站（Dest / Target）**。

整个交互流程如下图所示：

```
+-----------+                    +--------------------+                    +---------------------+
| 客户端    |                    | 你的 VPS (Reality) |                    | 真实目标网站 (如 Apple)|
+-----------+                    +--------------------+                    +---------------------+
      |                                     |                                         |
      | 1. ClientHello (带 SNI=apple.com)    |                                         |
      |    并在扩展中植入私钥加密认证 AuthData |                                         |
      |------------------------------------>|                                         |
      |                                     | 2. 校验 AuthData 是否合法?               |
      |                                     |                                         |
      |   [情况 A: 正常用户 (合法 AuthData)] |                                         |
      |   - 握手成功，直接建立加密代理隧道   |                                         |
      |   - 流量直奔代理目标                 |                                         |
      |                                     |                                         |
      |   [情况 B: GFW 审查/主动探测包]      |                                         |
      |   - 校验失败! (没有合法客户端私钥)   |                                         |
      |   - 不回显错误, 而是透明反向代理!    | 3. 原样透传 TLS 握手请求                 |
      |                                     |---------------------------------------->|
      |                                     | 4. 获取真实 Apple 官方证书与响应        |
      |                                     |<----------------------------------------|
      | 5. 将 Apple 官方响应回传给 GFW 探测器 |                                         |
      |<------------------------------------|                                         |
```

### 1. 握手阶段与身份鉴权
客户端发起正常的 TLS 1.3 握手，在其 `ClientHello` 报文的扩展填充中，利用服务端的 **公钥（Public Key）** 对自己的认证数据（包含预设的 ShortId 和时间戳）进行加密。

在外部嗅探设备（GFW）眼里：
* 这只是一个向 `apple.com` 发起的标准 TLS 1.3 握手请求，没有任何异样。

### 2. 遭遇 GFW 主动探测时的“绝妙伪装”
当 GFW 怀疑该 IP 有猫腻，主动发包探测时：
* 探测包不可能携带正确的客户端密钥和认证信息；
* Reality 服务端**绝不主动断开连接，也不返回任何代理服务特有的错误信息**；
* 而是像一个完全透明的代理一样，把 GFW 的探测流量原封不动地发给苹果官方服务器，再把苹果返回的真实证书和响应原样回传给 GFW。
* **探测结果**：GFW 的检测程序扫描后发现，这个 IP 无论是证书链、握手行为、回包时间，还是 HTTP 响应头，完完全全就是一台真实的苹果官方服务器！

## 三、Reality 的关键配置参数解读

在现代客户端（如 Sing-box、Mihomo / Clash Verge Rev）中，一个典型的 Reality 节点配置通常包含以下要素：

| 参数名 | 含义与作用 |
| :--- | :--- |
| `server` | 你的海外 VPS 真实 IP 地址 |
| `port` | 监听端口（通常强烈建议设为标准的 `443`，最贴合真实 HTTPS 流量） |
| `uuid` | 用户的鉴权身份标识（用户 ID） |
| `server_name` / `sni` | **借壳的合法大厂域名**（如 `www.lovelive-anime.jp`、`gateway.icloud.com`） |
| `public_key` | 服务端生成的公钥（用于客户端在握手初期加密鉴权凭证） |
| `short_id` | 短 ID 标识，增加被动识别的复杂度 |
| `spider_x` | 爬虫抓取的目录路径模拟，让访问特征更加逼真 |

## 四、如何挑选优质的“借壳目标（SNI）”？

选对借壳目标是 Reality 稳定运行的核心生命线。优质的目标域名通常满足：

1. **必须支持 TLS 1.3 与 H2 (HTTP/2)**：可在本地用终端执行 `curl -Iv https://目标域名` 查看协议支持。
2. **目标服务器 IP 物理位置要靠近你的 VPS**：例如你的 VPS 在东京，借壳目标最好也是在日本本地机房部署了 CDN 节点的站点（网络延迟越低，握手透传越逼真）。
3. **不能是被 GFW 已经列入黑名单阻断的站点**：你不能借用 `google.com` 或 `twitter.com`，因为它们自身在境内就已经被解析污染或阻断，必须选择**在国内能正常直接访问且无阻碍的大型合规境外网站**。
4. **排除使用了 Cloudflare CDN 的站点**：因为 CF CDN 的握手行为被深度关注，且 IP 频繁重定向，容易影响 Reality 的伪装纯净度。

## 五、总结与评价

* **优势**：
  * 彻底终结了“买域名、配证书、自建建站”的繁琐流程；
  * 从根本上免疫了 GFW 几年来赖以成名的**“主动探测”**绝技；
  * 基于纯 TCP/TLS，与国内三大运营商的 TCP 策略天然兼容，连接极其稳定。
* **局限**：
  * 由于底层依旧建立在 TCP 之上，遇到跨海长距离、高丢包、网络剧烈波动的场景，依然会受到 TCP 丢包重传的物理规律制约。想要在弱网环境下追求极致跑分与 4K 秒开，则需要由下一章介绍的 **Hysteria 2 / TUIC** 接棒。
